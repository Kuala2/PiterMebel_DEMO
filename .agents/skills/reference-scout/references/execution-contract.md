# Контракт выполнения Reference Scout для разных агентов

Работай по возможностям среды, а не по названиям инструментов конкретной модели:

- search/web получает URL;
- interactive browser/computer use быстро смотрит динамические страницы;
- `capture.mjs` создаёт стандартизированные доказательные PNG;
- image viewer/vision сравнивает PNG в полном размере;
- `board.mjs` собирает одинаковые поверхности рядом;
- отдельный reviewer используется только когда среда действительно даёт независимый read-only контекст.

Если exact-инструмента нет, используй функциональный эквивалент. Если нет обязательной возможности захвата или просмотра PNG, остановись с конкретной причиной; текстовые описания не заменяют визуальные доказательства.

## Порядок, устойчивый к слабым моделям

1. Прочитать `BRIEF.md` и назвать недостающие дизайн-поверхности.
2. Собрать дешёвый URL-инвентарь; не делать глубокий capture каждому найденному сайту.
3. Быстро отсеять кандидатов по реальному просмотру.
4. Захватить одинаковые home desktop+mobile только у восьми сильнейших.
5. Открыть PNG, сформировать `POOL.json`, собрать `board-pool`, пройти `research-pool` и остановиться.
6. Записать короткую пользовательскую классификацию в `POOL_SELECTION.json`.
7. Только после `continue` снимать внутренние страницы четырёх финалистов, извлекать фрагменты и завершать Research.

Не выбирать сайт по сниппету, названию, награде или собственному текстовому описанию. Не повторять заблокированный URL больше лестницы отказа. Не продолжать после пользовательской точки остановки.

## Передача между агентами

Артефакты в `.design/research/` являются состоянием задачи. При `возобнови` сначала проверь их и гейт; не начинай discovery заново, если `research-pool` уже прошёл и пользовательский выбор сохранён. Старый отчёт агента без соответствующего файла не считается состоянием.
