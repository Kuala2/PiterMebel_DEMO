# Этапы v12

## 0. Brief

Если пользователь дал сайт, VK/соцсеть, каталог или другую публичную базу клиента, сначала полностью прочитай [client-source.md](client-source.md). Это отдельный поток от поиска дизайн-референсов.

Создай `.design/BRIEF.md`:

1. **Режим проекта** — `PROJECT_MODE: COMMISSIONED` для реального заказчика/бизнеса или `PROJECT_MODE: CONCEPT` для вымышленного/spec-проекта.
2. **Факты** — только подтверждённое пользователем: продукт, город, аудитория, режим (showcase/commercial), доступные фото, желания. Отдельным блоком **Неизвестное** — всё, что нельзя выдумывать: цены, сроки, гарантии, метрики, адреса, бренды материалов. В дизайне и текстах неизвестное остаётся явным `[полем]`.
3. **Маршруты** — таблица: маршрут → тип страницы → единственная задача → главный вопрос клиента → главное действие.
4. **UX-каркас** — по каждому маршруту: вопросы клиента по порядку, доказательства, возражение→ответ, CTA. Один маршрут = одно главное действие.
5. **Визуальный тезис** — 3 наблюдаемых свойства желаемого впечатления и 5 анти-качеств (что сделает результат неприемлемым).
6. **Отношение к бренду** — для `COMMISSIONED` перенеси из `CLIENT_SOURCE.md` `BRAND_MODE`, повторяющиеся сигналы, конфликты и границу между узнаваемостью клиента и разовым оформлением соцсетей. Не объявляй редизайн логотипа частью сайта без явного разрешения.

Гейт: `gate.mjs --stage brief`. Стоп: пользователь подтверждает бриф одной фразой.

## 1. Research

1. Запусти `reference-scout` (его SKILL.md — там весь процесс). Сначала он создаёт `DISCOVERY.md`, `POOL.json`, home+mobile захваты восьми кандидатов и `board-pool.png`.
2. Запусти `gate.mjs --stage research-pool`, покажи только `board-pool` и остановись. Пользователь не ищет сайты: он отмечает подготовленные варианты как близкие, неподходящие или нейтральные. Запиши ответ в `POOL_SELECTION.json`. При `replace-pool` разрешён один новый пул, затем обязательная остановка.
3. Только после пользовательского `decision: continue` продолжи глубокий Research: 4 финалиста, две внутренние страницы каждого, REFERENCES.md и фрагменты.
4. Напиши `.design/SYNTHESIS.md`:
   - **Тезис проекта** — одно специфическое утверждение: `правда бизнеса → обещанное ощущение → визуальное поведение`. Если тезис без изменений подходит салону красоты и мебельной мастерской — он слишком общий.
   - **Ядро** — 5–7 строк: логика сетки, характер типографики (роль, не шрифт), плотность/воздух, характер медиа, движение.
   - **Визуальный якорь** — назови финалиста роли `visual-anchor` и объясни, какие свойства обеспечивают цельность home/listing/detail/mobile. Якорь задаёт непрерывность системы, но не копируется буквально.
   - **Ограничение влияния** — что именно art-direction источник не имеет права определять (например весь UX-каркас, все поля или все страницы), чтобы один эффект не захватил сайт.
   - **Поверхность → фрагмент** — hero, listing, detail, proof, CTA, mobile: на каждую максимум 2 фрагмента (структура + характер) из разных источников, с одним предложением, как свойство преобразуется под этот проект (минимум два преобразования: другой масштаб/ось, другая медиароль или другое поведение).

Гейт: `gate.mjs --stage research`. Стоп: покажи борды и SYNTHESIS.md.

## 2. Direction

Полностью прочитай [direction-contract.md](direction-contract.md) и выполни его до гейта.

До создания первого concept HTML запусти `gate.mjs --stage direction`. Для нового Direction ожидаем `GATE_FAIL` только по отсутствующим выходам самого Direction; любая ошибка `PRE_DESIGN_NOT_READY` означает, что сначала нужно закончить Client Intelligence или Research. Не компенсируй недостающие клиентские данные stock-контентом без явного waiver пользователя.

1. Сначала собери `.design/media/project-media.json` и `project-media-board.png`. Без разрешённых реальных изображений остановись со статусом `MEDIA_REQUIRED`; геометрические `PHOTO SLOT` не заменяют контент.
2. Прочитай `SYNTHESIS.md`, `FRAGMENTS.md`, полноразмерные fragment PNG, раздел `Визуальная идентичность` из `CLIENT_SOURCE.md` и, если есть, `.design/REJECTED.md`. Не выбирай направления из заранее заданного меню стилей. Сформулируй три гипотезы из наблюдаемых отношений в референсах и зафиксируй их вместе с `sourceFragments`/`sourceTransfers` и `brandTreatment` в `.design/style-lab/DIRECTION_CONTRACTS.json`.
3. Создай `concept-{1,2,3}.html`. Каждый — автономный компактный **system sampler**, а не готовая длинная главная: header + hero + переход, один listing/project модуль, один detail/proof модуль и CTA. Этого достаточно, чтобы проверить грамматику home/listing/detail и mobile; полный маршрут появится на Page Targets. Реальный кириллический контент из брифа и минимум два реальных файла из media manifest в каждом концепте.
4. У каждого концепта — **свои provisional-токены** в комментарии в начале файла: `<!-- TOKENS: bg #…, ink #…, accent #…; display …; body …; spacing …; radius …; motion … -->`. Обязательные для всех: кириллические шрифты (проверь сабсеты), контраст-пары, accessibility, одна шкала отступов.
5. Концепты обязаны различаться минимум по пяти осям контракта и по композиционному семейству. Не используй один и тот же skeleton с заменой serif/sans, цвета, вертикального индекса или размера заголовка. У каждого — свой набор фрагментов и одна продуктовая signature idea.
6. Сними и посмотри сам:
   ```bash
   node <scout>/scripts/capture.mjs file .design/style-lab/concept-1.html .design/style-lab/concept-2.html .design/style-lab/concept-3.html --out .design/style-lab/shots
   ```
   Открой PNG в читаемом масштабе, прогони по чек-листу quality-floor. Исправь наблюдаемые проблемы (одна итерация) и пересними.
7. Собери `concept-board.png` и `.design/style-lab/reference-trace-board.png`: для каждого концепта рядом должны быть видны использованные fragment PNG и desktop/mobile output. Без визуальной пары source→output текстовые заявления о заимствовании не считаются доказательством.
8. Назначь отдельного read-only reviewer. Передай ему не только Brief и output, но также `SYNTHESIS.md`, `FRAGMENTS.md`, fragment PNG, media board, reference-trace-board и `.design/REJECTED.md`, если он существует. Reviewer обязан проверить reference fit, риск AI-default и повторяемость с отклонёнными решениями; затем назвать recommended и weakest и отправить минимум одно направление в `rework` или `reject`.

После выбора пользователем:
- `.design/ACCEPTED.md` — что выбрано и почему, ссылки на HTML+PNG;
- `.design/REJECTED.md` — что отвергнуто и почему (для будущих итераций);
- `.design/DESIGN_TOKENS.md` — **извлеки токены из выбранного концепта** (из его `<!-- TOKENS -->` и фактического CSS) по формату [design-tokens.md](design-tokens.md). С этого момента токены зафиксированы и меняются только новой записью в ACCEPTED.md.

Гейт: `gate.mjs --stage direction`.

## 3. Page Targets

1. `.design/ROUTE_CONTRACTS.md` — по каждому маршруту: задача, последовательность секций с их section contract (`вопрос клиента → доказательство/инструмент → визуальный центр → действие`), назначенные фрагменты, mobile-приоритет.
2. Полная главная как автономный HTML в `.design/targets/home.html`. Затем отдельные targets для каждого уникального типа страницы из брифа (listing, detail, service, process, contacts…). Не размножай одну композицию: общие — токены и атомы (кнопки, поля), разные — композиции страниц.
3. Каждая крупная секция отвечает на новый вопрос и имеет визуальный центр (реальное медиа, сравнение, данные, инструмент). Одноцветная плоскость с текстом — не секция.
4. Состояния: у кнопок и полей — hover, focus-visible, active, disabled, error. В targets они обязаны существовать.
5. Сними с сегментами:
   ```bash
   node <scout>/scripts/capture.mjs file .design/targets/*.html --out .design/targets/shots --segments
   ```
   (если glob не раскрылся — перечисли файлы явно). Прогони чек-лист quality-floor по сегментам каждого маршрута. Одна пакетная итерация исправлений.
6. Собери route-target-board и покажи пользователю: `board.mjs .design/targets/shots --out .design/targets/board.png --cols 3`.

Гейт: `gate.mjs --stage targets`. Стоп: пользователь утверждает весь набор или возвращает на переработку. Production-код до утверждения не меняется.

## 4. Build

1. Перенеси токены из DESIGN_TOKENS.md в проект (CSS-переменные/Tailwind-конфиг). Один источник истины.
2. Собери атомы один раз: кнопка, поле, карточка-контейнер, типографические классы — со всеми состояниями.
3. Реализуй по одному шаблону за раз: открой target и его скриншот рядом → сверстай → сними production-страницу в том же viewport → сравни наблюдаемо (композиция, отступы, типографика, кадры) → исправь drift → следующий. Максимум 2 итерации на страницу; если не сходится — вернись к target, а не импровизируй в коде.
4. Для редизайна: чистый слой стилей; старые visual entrypoints удаляются из импортов, а не перекрываются.
5. Функции, данные и тексты брифа сохраняются. Ничего из targets не «улучшается» на ходу.

## 5. QA

1. Подними production-сборку локально. Создай `.design/qa/routes.json`:
   ```json
   { "base": "http://127.0.0.1:3000",
     "routes": [{"name":"home","path":"/"}, {"name":"listing","path":"/projects"}] }
   ```
2. `node <root>/scripts/audit.mjs --config .design/qa/routes.json` — детерминированный аудит: overflow на 320–1440, контраст, цели нажатия, focus-visible, alt, пустые страницы, JS/HTTP ошибки, скриншоты. Отчёт: P0/P1/P2. Лимит — 2 прогона на QA-цикл (цикл по умолчанию `main`, скрипт следит сам). Новый цикл (`--cycle <имя>`) открывается только по явной просьбе пользователя о новом раунде правок — агент не вправе перезапускать бюджет сам.
3. Собери один пакет исправлений (P0 все, P1 по возможности), исправь одним проходом.
4. Второй и последний `audit.mjs`. Дальше — стоп:
   - нет P0 → `READY_FOR_USER_REVIEW`;
   - остались P0/P1 → `NEEDS_REVIEW` со списком.
5. Сравни финальные скриншоты с targets рядом (тот же viewport) и зафиксируй оставшийся drift в `.design/qa/CRAFT_NOTES.md` — наблюдаемо, без оценок числами.
6. Заполни `.design/DELIVERY.json`:
   ```json
   { "mode": "showcase",
     "routes": [{"path": "/", "audit": ".design/qa/run-02/audit.json"}],
     "sources": ["app"],
     "contacts": null }
   ```
   Гейт: `gate.mjs --stage release`. P0 блокируют всегда. P1 тоже блокируют release: либо исправь их, либо пользователь осознанно принимает их, записав список в `.design/qa/WAIVER.md` (что принято, почему) — гейт это учитывает. P2 остаются в отчёте.

Никаких числовых оценок, рекурсивных ревью и автоматических продолжений после второго прогона.
