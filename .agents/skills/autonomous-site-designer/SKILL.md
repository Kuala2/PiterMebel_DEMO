# Autonomous Site Designer v12

Скелет системы: дизайн-решения фиксируются ДО кода (токены → HTML-targets), реализация переносит их без отсебятины, машина проверяет то, что можно проверить машиной, пользователь делает короткие визуальные выборы из уже подготовленных вариантов. Пользователь не обязан сам искать референсы.

## Канонический источник

- Актуальная пользовательская установка хранится в `C:\Users\Titar\Desktop\Site-Design-System\skills`; пути Codex, Gemini и подключённых проектов являются junction-ссылками на неё.
- Не копируй skills из других проектов и особенно из `Site demo/.agents`: это архивные версии. Старые указания «сначала скопируй skills в проект» считать отменёнными.
- Для полного сайта обязательны оба skill: этот orchestration-skill и `reference-scout`. Если `reference-scout` недоступен, остановись со статусом `SKILL_SET_INCOMPLETE`; не заменяй его памятью модели.
- До работы зафиксируй `PROJECT_MODE: COMMISSIONED` для реального заказчика/названного бизнеса или `PROJECT_MODE: CONCEPT` для вымышленного/spec-проекта. В режиме `COMMISSIONED` дизайн не начинается, пока клиентский источник не прошёл pre-design readiness; Reference Research при этом может идти независимо.

Прочитай по ходу работы:
- [references/execution-contract.md](references/execution-contract.md) — всегда первым: как определить активный этап, сопоставить инструменты разных агентов и возобновить работу;
- [references/stages.md](references/stages.md) — этапы (обязательно, по одному разделу на этап);
- [references/client-source.md](references/client-source.md) — на Brief, если пользователь дал сайт, соцсеть, каталог или другой источник информации о клиенте; включает аудит фактов, медиа и существующей визуальной идентичности;
- [references/design-tokens.md](references/design-tokens.md) — перед Direction;
- [references/direction-contract.md](references/direction-contract.md) — перед Direction; реальные медиа, различимость трёх направлений и независимое сравнительное ревью;
- [references/quality-floor.md](references/quality-floor.md) — перед Direction, Targets и QA.

`<root>` — папка этого SKILL.md. Скрипты запускай из корня проекта; там же должен стоять playwright (`npm i -D playwright && npx playwright install chromium`).

## Непереговорные правила

- Один этап за одну задачу. Закончил — остановись на контрольной точке. Никаких бесконечных циклов и самопроверок.
- Явный scope пользователя выше автоматического workflow. `Возобнови` продолжает первый непрошедший переход; `с нуля` не разрешает молча удалять старые файлы.
- Названия инструментов не являются требованиями: используй функциональный эквивалент среды. Артефакты и гейты одинаковы для Codex, Gemini и GLM/ZCode.
- Не трогай production-код до утверждения page targets пользователем.
- Референсы — это PNG-скриншоты, а не воспоминания о сайтах. Нет скриншота — нет референса. На Direction каждый заметный композиционный перенос должен быть доказан source→output, иначе референс считается неиспользованным.
- Факты бизнеса не выдумываются: неизвестное остаётся `[полем]` в BRIEF.md до подтверждения пользователем.
- Никаких числовых оценок красоты и вердиктов «премиально». Только наблюдаемое на скриншотах и вердикты скриптов.
- Одна смелая идея на страницу (signature element), всё остальное — тихо. См. quality-floor.
- Бан-лист анти-паттернов из quality-floor.md обязателен на всех этапах дизайна.
- Дизайн живёт в токенах и HTML-targets. У каждого концепта — свои provisional-токены; после выбора пользователя `DESIGN_TOKENS.md` извлекается из победителя и дальше не меняется без записи в ACCEPTED.md.
- QA — максимум 2 прогона `audit.mjs` на этап (скрипт сам следит за лимитом). После второго — остановка и отчёт. P0 и P1 блокируют release; P1 можно принять только явным waiver пользователя (`.design/qa/WAIVER.md`).

## Этапы и контрольные точки

1. **client intelligence (только COMMISSIONED)** — официальный source registry, полный доступный контент, товары/услуги, контакты, тексты, медиа максимального доступного качества и аудит бренда. Поток может выполняться до/параллельно Research, но обязан иметь `SOURCE_READINESS: COMPLETE` до Direction.
2. **brief** — `.design/BRIEF.md`: режим проекта, факты/неизвестное, маршруты, вопросы клиента, анти-качества. Стоп: пользователь подтверждает бриф.
3. **research-pool** — `reference-scout` автономно собирает широкий URL-инвентарь, отсеивает его до 8 сильных home+mobile кандидатов и показывает `board-pool`. Стоп: пользователь быстро отмечает понравившиеся/неподходящие; искать URL ему не нужно.
4. **research** — только после `POOL_SELECTION.json`: глубокие страницы 4 финалистов, фрагменты и `.design/SYNTHESIS.md`. Стоп: пользователь смотрит итоговые борды.
5. **pre-design readiness** — перед Direction машина проверяет одновременно: утверждённый Brief, завершённый Research и, для `COMMISSIONED`, полный клиентский intake/медиа/brand audit. Неполный источник не мешает Research, но блокирует генерацию концептов.
6. **direction** — реальный media board, подтверждённое отношение к существующему бренду, 3 компактных system-sampler концепта, визуальная трассировка от фрагментов к результату и независимое сравнительное ревью; после выбора — `DESIGN_TOKENS.md` из победителя. Готовые архетипы до анализа Research, длинные псевдосайты, заглушки и три вариации одной AI-грамматики блокируют этап. Стоп: пользователь выбирает один или отклоняет все.
7. **page-targets** — `ROUTE_CONTRACTS.md` + полные HTML-targets всех уникальных типов страниц со скриншотами (desktop+mobile). Стоп: пользователь утверждает набор.
8. **build** — перенос targets в production постранично: target → код → скриншот → устранение drift → следующая. Гейт `gate.mjs --stage build`.
9. **qa** — `audit.mjs` → пакет P0/P1/P2 → исправление → второй `audit.mjs` → стоп: `READY_FOR_USER_REVIEW` или `NEEDS_REVIEW`.

Гейты готовности накопительные: `node <root>/scripts/gate.mjs --stage brief|research-pool|research|direction|targets|build|release`. Поздний этап заново проверяет обязательные входы предыдущих. GATE_FAIL = переходить дальше нельзя.

## Скрипты

```bash
# скриншоты локальных HTML (концепты, targets):
node ../reference-scout/scripts/capture.mjs file concept-1.html concept-2.html --out .design/style-lab/shots --segments
# борды:
node ../reference-scout/scripts/board.mjs <папка|файлы> --out board.png --cols 3
# инвентарь проектных фото:
node ../reference-scout/scripts/board.mjs --media public --out .design/media
# детерминированный аудит (QA):
node <root>/scripts/audit.mjs --config .design/qa/routes.json
# гейт этапа:
node <root>/scripts/gate.mjs --stage <stage>
# самотест системы (из проекта с playwright):
node <root>/scripts/selftest.mjs
```

Если путь до reference-scout неизвестен (скилл скопирован в проект), используй ближайшую копию его scripts/ — контракты те же.

## Связь с другими skills

- `reference-scout` владеет сбором референсов; его скрипты — единственный способ захвата скриншотов в этой системе.
- `impeccable` (если установлен) — только дополнительный сигнал в QA (`npx impeccable detect`), не заменяет audit.mjs.
- Любой дизайн-canvas skill допустим на Direction/Targets, но его драфты обязаны стать локальными HTML-targets и пройти выбор пользователя.
